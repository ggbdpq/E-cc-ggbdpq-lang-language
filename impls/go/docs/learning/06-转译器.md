# 06 - →Go 转译器：一门语言，两种执行方式

## 一句话定义

转译器（transpiler）把 lang-go 源码翻译成 Go 源码：语义不变，换一种说法。从此同一份 .lang-go 文件有两条执行路径——解释器直接跑（开发时），Go 编译后跑（发布时），两条路径的输出必须逐字节一致。

## 三个核心要素

**1. 转译的本质是"映射表 + 逃生舱"。**
 lang-go 的每个概念在 Go 里都有一个对应物：struct 映射原生 Go struct（值语义白拿）、闭包映射 Go 闭包、`?` 展开成 `if !r.ok { return LangGoResErr[...](r.e) }`。映射不了的（`map` 这种撞 Go 关键字的用户名）靠机械规则绕开：函数统一加 `lf_` 前缀、构造器加 `le_` 前缀。看 `internal/gen/gen.go` 的 `goTypeWith` 和 `emitCall`，就是两张映射表的代码形态。

**2. 没有类型检查器也能生成类型正确的代码——借宿主编译器的力。**
 lang-go v0 不做静态类型检查，但生成的 Go 代码必须类型正确。诀窍有二：一是**转译约束**——参数必须注解、`?` 只能在语句顶层，违反就在转译期报错（每条约束都对应"没有这个信息就写不出 Go 签名"的硬缺口）；二是**最小推断**——`infer` 函数只推断"够用"的类型信息（字面量、构造器、已知函数签名），推断不出的就按 `any` 处理，在 any 与具体类型交界处自动插 `langGoTo[T]` 断言。类型安全的兜底人是 Go 编译器：生成代码编译不过 = 转译器缺陷。

**3. 等价验收把"跑通了"变成机械判定。**
 →Go 后端怎么证明正确？`gen_test.go` 的做法：同一份 lang-go 源码，解释器跑一遍收集 stdout，转译成 Go 再编译执行收集 stdout，两个字符串逐字节比对。这一个测试同时看住三层：生成的代码必须能编译（Go 编译器把关）、必须能跑（运行时把关）、行为必须和解释器一致（语义把关）。prelude 里的格式化函数因此必须逐字节镜像解释器的 `fmtVal`——连浮点打印的 `3.14159` 和 `5` 都不能差。

## 最容易混的误解

误解：转译是"简单替换"，比写解释器容易。
真实成本分布反过来了：解释器难在语义（环境链、值语义、控制流信号），转译器难在**边界**。本次实现里真正的坑全在两种语言的接缝上：Go 的实参表里换行必须跟逗号（函数字面量内嵌进 `println(...)` 时多一个尾随换行就编译失败）；Go 的 `switch` 没有 default 时函数报 missing return（穷尽检查保证了逻辑不可达，仍要补 `panic` 才能编译）；Go 的 `append` 可能重分配切片，破坏 lang-go "push 原位变更、别名可见"的语义——所以数组要包一层 `*LangGoArr[T]`。每个接缝坑都是一次红→绿循环修掉的。

第二个误解：有了转译器就可以扔掉解释器。解释器是转译器的**参照系**：等价测试的一方就是它。没有解释器，转译器对不对只能靠人眼看 Go 代码。

## 在本项目里看什么

- `internal/gen/gen.go`：`goTypeWith`（类型映射）、`infer`（最小推断）、`emitCall`（内建/构造器/函数/方法四路分发）、`genTry`（`?` 的编译期展开）、`checkExhaustive`（穷尽检查从运行时前移到编译期的落点）。
- `internal/gen/prelude.go`：约 300 行的 Go 运行时镜像。对照 `internal/interp/value.go` 的 `fmtVal` 读——两个文件的格式化逻辑逐行对应，这是等价测试成立的前提。
- `internal/gen/gen_test.go`：四条转译约束测试 + `Test等价_示例程序`（对 examples 全部四个程序做端到端等价）。
- `examples/closures/main.lang-go`：注意它的注解密度——这是按"可转译"标准写的 lang-go，与"解释器友好"的写法差异就在注解上。

## 行业对照

TypeScript→JS、Haxe→多目标、Scala.js 都是转译路线，共同点是**把执行外包给目标平台，语言只负责翻译**。TypeScript 的设计哲学"types are erased"（类型擦除）在这里同样适用：lang-go 的注解在转译期用完即扔。转译路线最大的坑也和 TypeScript 一样——目标平台升级（Go 泛型、JS 新标准）既是红利也是迁移负担。
