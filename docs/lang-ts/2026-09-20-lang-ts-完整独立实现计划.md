# 2026-09-20-lang-ts-完整独立实现计划

> 项目：`lang-ts`  
> 定位：使用 TypeScript 独立实现与 lang-go 同一门语言  
> 目标：一次性达到当前 lang-go 完整能力面，并在 v0.9 完成后通过最终契约同步  
> 工作模式：Full-Parity Working Tree，开发阶段不提交 Git


## 0. 最高优先级约束

本项目是 **lang-go 的独立实现（independent implementation）**。`lang-py` / `lang-ts` 只表示编译器自身使用的宿主语言，所实现的源语言、语法、静态语义、动态语义、诊断协议、Agent Contract 和 Conformance Contract 必须与 lang-go 保持一致。

### 0.1 一次性完整复刻，开发期间禁止提交

本轮采用 **Full-Parity Working Tree** 模式：

```text
侦察 lang-go 当前完整能力
        ↓
一次性实现完整 lang-py / lang-ts
        ↓
持续测试、修复、对齐
        ↓
v0.9 最终契约同步
        ↓
全量 Conformance / Differential / Contract 验证
        ↓
输出建议 Commit Plan
```

整个实现阶段：

```text
禁止 git init
禁止 git add
禁止 git commit
禁止 git tag
禁止 git push
禁止 cherry-pick
禁止 rebase
禁止照着 lang-go 的历史提交逐个复刻
```

如果目标目录已经处于 Git 仓库中，也不得修改 Git 历史或创建提交。

所有代码先连续保留在工作区。只有完整复刻通过最终验收后，输出一份“建议如何拆分提交”的 Commit Plan，**本轮不执行任何提交**。

这样做的目的，是让 Python / TypeScript 实现围绕当前完整语言契约设计，而不是被 lang-go 的历史重构路径绑架。

### 0.2 v0.9 并行开发同步规则

lang-go 的 v0.9 正在另一个工作流中实施，因此：

1. 开工时读取 lang-go 当前 HEAD、现有 v0.1～v0.8 计划以及 v0.9 Draft。
2. 对稳定部分直接实现。
3. 遇到 v0.9 尚未最终裁定的语义，不允许自行发明答案，记录为 `SPEC-GAP`。
4. 不因为 `SPEC-GAP` 阻塞其他稳定模块的开发。
5. 最终验收前必须重新读取 lang-go 最新：
   - `specs/`
   - Rule Catalog
   - diagnostics contract
   - Agent Contract / schemas
   - `conformance/`
   - runner contract
   - v0.9 最终 ADR
6. 做一次 **Final Contract Sync**，关闭全部可关闭的差异。
7. 只有最终 lang-go Conformance Contract 能裁决语义，Go 内部源码只能作为实现参考，不能成为最高规范。

### 0.3 禁止“翻译 Go 代码”

允许阅读 Go 实现以理解工程行为和发现遗漏，但禁止：

```text
Go struct 逐个翻译
Go 文件逐个翻译
Go package 机械映射
Go 控制流逐行复制
Go 私有 helper 直接复制
```

应采用宿主语言最自然、最成熟的工程范式重新实现相同语义。

最终比较的是：

```text
Valid / Invalid Decision
Name Binding
Type Result
HIR / IR Semantic Meaning
Diagnostics Identity
Observable Runtime Behavior
Agent Contract
Conformance Result
```

不是源码长得像不像 Go。

## 2. TypeScript 工程原则

采用现代 Node.js + TypeScript 严格工程模型。

建议：

```text
package.json
pnpm-lock.yaml
tsconfig.json
src/
tests/
```

TypeScript 配置要求：

```text
strict: true
noImplicitAny: true
noUncheckedIndexedAccess: true
exactOptionalPropertyTypes: true
useUnknownInCatchVariables: true
```

核心设计优先：

- discriminated unions 表达 AST / HIR / IR。
- `readonly` 保持语义模型不可变。
- branded types 表达 NodeId / SymbolId / DiagnosticCode。
- exhaustive `switch` + `never` 保证节点处理完整。
- Semantic Core 使用纯函数或显式 context。
- 明确区分 `unknown` 与语言自身的 `Any/Unknown`。
- 禁止 TypeScript `any` 偷穿语言类型系统。
- ESM / CJS 选择一次后保持一致，优先项目当前主流配置。
- Node API 只放在 IO / CLI / runner 层。

测试和开发工具建议：

```text
Vitest
ESLint 或 Biome（结合现有环境选择）
tsc --noEmit
```

不要为简单 CLI 引入重型框架，Node 内置 `parseArgs` 足够时优先使用。

## 13. Phase J：TypeScript 特有风险审查

### `any` Leakage

核心 compiler 包原则上零 `any`。确实不可避免时，必须限定到 adapter 边界并马上收窄。

### `undefined` / `null`

宿主的 `undefined/null` 不得成为 lang-go Option/nullability 的隐式实现语义。

### Number Semantics

JavaScript `number` 与语言 int/float 规则可能不同。

必须按 canonical spec 实现：

```text
integer range
overflow policy
float behavior
equality
JSON numeric boundary
```

不能默认 JS Number 就是语言整数。

### Object Key Ordering

Map / object 的枚举顺序不能无意成为语言规范。

### Async Semantics

Promise/microtask 顺序不能私自定义 Task/Channel 行为。并发必须遵守 v0.9 canonical concurrency contract。

### UTF-16 Offset

所有 SourceSpan/Agent Contract offset 必须经过统一转换，不能把 JS string index 直接对外暴露。

### ESM Tooling

避免测试、CLI、generated JS 在 ESM/CJS 之间产生两套行为。
