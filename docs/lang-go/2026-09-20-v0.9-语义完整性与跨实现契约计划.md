# 2026-09-20-v0.9-语义完整性与跨实现契约计划

> 阶段定位：Semantic Integrity + Cross-Implementation Contract  
> 前置版本：v0.8 Verification  
> 目标版本：v0.9.0  
> 核心目标：让 lang-go 从“已经具备 Semantic Core 的语言工程”进入“拥有统一语义裁决体系的编程语言”。

---

## 1. 本阶段要回答的核心问题

v0.9 不以新增语法和新增工具为主，而要系统回答下面四个问题：

1. 这门语言的每一条规则是否彼此一致。
2. 同一段合法程序的行为是否可解释、可预测。
3. Compiler、Human、Coding Agent 是否能引用同一条语义规则得到同一个结论。
4. Go、Rust、TypeScript、Python 等独立实现是否仍然实现同一门语言。

最终目标：

```text
Human
  ↓
自然、稳定、接近传统语言的源码体验
  ↓
Language Specification
  ↓
Semantic Contract
  ↓
Compiler Semantic Core
  ↓
Agent Contract
  ↓
Conformance Suite
  ↓
Go / Rust / TypeScript / Python
```

任何实现冲突最终由 Language Specification 与 Conformance Suite 裁决。

---

## 2. v0.9 的最高设计原则

### 2.1 Human First

Human 编写代码时应获得传统编程语言的核心体验：

- 语法稳定
- 控制流直观
- 类型规则可理解
- 错误位置准确
- 错误信息可行动
- 模块边界明确
- 隐式行为尽可能少
- 格式化结果稳定
- 同一代码在不同实现中保持相同语义

Agent 友好能力优先进入：

```text
Semantic Model
HIR / IR
Agent Protocol
Semantic Graph
Diagnostics
Refactoring API
Verification
```

普通源码不应为了机器分析而变得晦涩。

### 2.2 Compiler Strict

Compiler 必须能对每个程序给出稳定结论：

```text
Valid
Invalid
Platform Restricted
Implementation Defined
```

尽量减少模糊状态。

以下行为必须明确：

- name resolution
- type compatibility
- generic instantiation
- value semantics
- reference semantics
- Result / Option
- match
- module visibility
- import resolution
- evaluation order
- side effects
- concurrency
- FFI boundary
- runtime failure

### 2.3 Agent Precise

Coding Agent 不应通过文本猜测理解语义。

Agent 需要能够查询：

```text
symbol
type
reference
definition
caller
callee
effect
dependency
impact
diagnostic
ruleId
sourceSpan
```

所有关键语义事实都必须能追溯到具体源码范围与规范规则。

### 2.4 Multi Implementation Consistency

Go 继续作为 Reference Implementation。

未来：

```text
Go
Rust
TypeScript
Python
```

可以采用不同内部架构，但必须共享：

```text
Language Specification
Rule IDs
Diagnostic Contract
Agent Protocol
Conformance Format
Observable Semantics
```

宿主语言能力不得反向定义 lang-go 语义。

# 4. 建立 Semantic Rule Catalog

所有重要规则拥有稳定 Rule ID。

建议命名：

```text
LEX-xxx
PARSE-xxx
NAME-xxx
TYPE-xxx
GEN-xxx
VALUE-xxx
CTRL-xxx
CALL-xxx
MATCH-xxx
RESULT-xxx
MODULE-xxx
TASK-xxx
CHAN-xxx
EFFECT-xxx
FFI-xxx
RUNTIME-xxx
```

示例：

```text
TYPE-ASSIGN-001
TYPE-CALL-003
NAME-SHADOW-002
MATCH-EXHAUSTIVE-001
RESULT-TRY-002
MODULE-VIS-001
TASK-SPAWN-001
```

每条规则至少包含：

```text
Rule ID
Title
Normative Statement
Preconditions
Semantics
Invalid Cases
Diagnostics
Examples
Conformance Cases
```

例如：

```text
Rule: TYPE-ASSIGN-001

如果表达式 e 的静态类型为 T，
变量 x 的声明类型为 U，
且 T assignable-to U，
则赋值 x = e 合法。
否则产生指定 diagnostic。
```

Rule ID 应进入：

- spec
- diagnostic metadata
- conformance manifest
- Agent Contract

这样 Human、Compiler 与 Agent 可以引用同一条规则。


# 6. Type System 收口

v0.9 必须形成可写入 v1.0 的类型系统定义。

## 6.1 明确类型类别

建议正式定义：

```text
Primitive
Array
Slice
Map
Struct
Enum
Function
Generic Parameter
Option
Result
Channel
Reference
Any
Unknown
Never
```

每种类型明确：

- equality
- assignability
- conversion
- inference
- member access
- generic behavior

## 6.2 区分 Any 与 Unknown

必须明确：

```text
Any
```

代表允许动态边界，并可能降低静态保证。

```text
Unknown
```

代表编译器当前无法确定类型，不能自动拥有任意能力。

禁止把二者长期作为“放行一切”的逃生口。

## 6.3 泛型策略

v1.0 前必须明确采用哪一种稳定策略。

建议优先：

```text
Static Generic Parameters
+
Erased Runtime Representation
+
Compile Time Constraint Checking
```

避免 v1.0 引入复杂 trait system。

至少支持明确的：

- generic declaration
- generic inference
- generic substitution
- invalid instantiation
- nested generic
- Option / Result generic behavior

## 6.4 Structural 与 Nominal

正式确认 v1.0 类型身份策略。

如果当前实现主要依赖 Symbol identity，建议 v1.0 定义：

```text
Struct / Enum 使用 nominal typing
Function 与部分容器使用 structural compatibility
```

未来再通过版本演进增加更广泛的 structural typing。

# 8. Evaluation Order

必须正式规定求值顺序。

例如函数调用：

```text
f(a(), b(), c())
```

需要明确：

```text
callee
argument 1
argument 2
argument 3
call
```

是否按左到右执行。

同时覆盖：

- binary expression
- boolean short circuit
- assignment
- method call
- indexing
- match
- function arguments
- collection literals

求值顺序是跨 Backend 一致性的核心。

# 9. Module System 收口

当前文件加载机制需要提升为真正语言模块语义。

至少定义：

```text
module identity
import resolution
namespace
public/private visibility
duplicate symbol
cyclic import
module initialization
cross-module type identity
```

建议 v1.0 采用小而清晰的模型。

示例方向：


是否采用 `pub` 由现有语法兼容性决定。

# 10. Concurrency Semantic Model

v0.9 的最高优先级问题之一。

当前 `go f()` 不应长期依赖 Go goroutine 的宿主语义。

语言层定义抽象：

```text
Task
Spawn
Yield
Block
Join
Channel
Send
Receive
```

后端映射：

```text
Language Task
   ↓
Go            goroutine
JavaScript    Promise / scheduler
Interpreter   cooperative scheduler
Rust          future / task / thread adapter
Python        coroutine / task adapter
```

具体宿主机制可以不同。

必须统一：

- spawn 是否立即执行
- 当前 task 是否继续
- send/receive 是否阻塞
- channel capacity
- close semantics
- panic/error behavior
- task completion
- deterministic guarantees
- unspecified scheduling behavior

将确定性语义与 scheduler 自由度分开描述。

# 18. 第二实现验证策略

Go v1.0 后优先开发 Rust Independent Implementation。

Rust 实现原则：

1. 只读取 `specs/`。
2. 只依赖 `conformance/`。
3. 不逐行翻译 Go。
4. 遇到规范缺失时记录 Specification Gap。
5. 不通过阅读 Go 内部代码偷偷补全语义。
6. 所有 Gap 先修复 Spec 与 Conformance，再继续实现。

Rust 实现本身将成为：

```text
Specification Completeness Test
```

随后再做：

```text
TypeScript
Python
```

# 26. v1.0 目标状态

最终希望形成：

```text
                    Language Specification
                            │
                     Semantic Rules
                            │
                ┌───────────┼───────────┐
                ↓           ↓           ↓
           Compiler      Agent       Human Docs
                │           │
                └───── Conformance ─────┘
                            │
              ┌─────────────┼─────────────┐
              ↓             ↓             ↓
             Go            Rust           TS
              │
            Python
```

Human 写起来保持传统语言的自然感。

Compiler 对程序拥有严格、统一的语义判断。

Agent 可以精确查询、修改和验证程序。

不同实现由同一套规范、规则编号和 Conformance Suite 裁决。

这就是 v1.0 前真正需要建立的语言身份。
