# 04 - 解释器：让语法树动起来

## 一句话定义

树遍历解释器（tree-walking interpreter）直接"走"语法树算出值：遇到加法节点就算加法，遇到调用节点就跳进函数体，不加任何中间产物——像照着菜谱一步一步做菜，菜谱（AST）本身就是执行计划。

## 三个核心要素

**1. 环境链决定"变量在哪"。**
每个函数调用、每个块都创建一个新环境（`Env`：一张变量表 + 指向父环境的指针），查变量沿父链向上找。闭包能记住出生地的环境，所以 `makeAdder(10)` 返回的函数永远记得 `n=10`。类比： 公司里找文件，先翻自己抽屉，没有就问部门，部门没有问公司。

**2. 值语义靠"拷贝时机"落实。**
ling 说"struct 赋值时拷贝"（spec §3.7），实现集中在 `value.go` 的 `copyValue`：绑定、传参、返回三个时机各调一次；嵌套 struct 递归拷贝，slice/map 字段共享。一个函数、一个规则，语言的性格就定了。指针（`&x`）是反方向的逃生舱：`PtrVal` 直接握着原变量的存储格，写它就是写原值。

**3. 控制流用"信号"穿过层层求值。**
`return`/`break`/`continue`/`?` 都是 Go 语言层面的特殊 error（`signal` 类型），在正确的边界被捕获：循环体消化 break/continue，函数边界消化 return，`?` 抛出的 Err 在**函数边界合成 `Err` 返回值**（`runBody` 里的 `sigErr` 分支）——这就是 `let n = parse(s)?` 能把错误一路送回调用方而中间代码零感知的机制。类比：酒店走廊里的紧急滑梯，每层楼有人接住该自己接的，没人接的一路滑到地面报警。

## 最容易混的误解

误解：解释器的第一目标是快。
v0 的第一目标是**正确 + 好改**。树遍历慢一个数量级，但代码量和语法的距离最短——ling 整个求值核约 900 行 Go，改语义就是改一个 switch 分支。CPython 0.9 也是树遍历起家，跑通了整个生态才换字节码。优化是给"被验证过的语义"做的手术，顺序反了就是在给未验证的设计抛光。

第二个误解：`?` 需要语言运行时支持。
ling 的 `?` 在解释器里只有两个动作：解包 `Ok`、或抛一个信号。真正的机制在函数边界"接住信号、合成返回值"。理解了这一点，M3 转译到 Go 时你就知道该生成什么代码。

## 在本项目里看什么

- `internal/interp/interp.go`：`eval` 大 switch 是全语言的语义索引；`callClosure`/`callMethod`/`runBody` 三件套是调用约定；`execLoopBody` 与 `runBody` 对信号的不同消化方式对比着读。
- `internal/interp/value.go`：`copyValue`（值语义）、`equals`（哪些类型可比）、`fmtVal`（println 的输出格式全在这）。
- `internal/interp/builtin.go`：`prelude` 里预载的 `Option`/`Result`/`error`——所谓"内建代数类型"，其实就是解释器启动时注册的三个普通定义，没有任何特权。
- 测试 `internal/interp/interp_test.go` 是行为规范：值语义拷贝、指针穿透、`?` 传播、match 穷尽，每个语义决定都有一个"名字即断言"的用例。

## 行业对照

执行策略光谱：树遍历（ling v0、Ruby 早期、CPython 0.9）→ 字节码 + VM（CPython 现代、Lua）→ JIT（V8、PyPy）。转译是光谱外的第四条路（ling M3、Haxe、TypeScript→JS），它把"执行"外包给目标平台，语言本身只负责翻译。ling 两条腿：v0 用树遍历钉死语义，M3 用转译接通生态。
