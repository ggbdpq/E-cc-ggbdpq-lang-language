# 05 - REPL 与测试工具：语言核外面那一圈

## 一句话定义

REPL（交互式解释循环）把"写一句、跑一句"变成可能；测试运行器把"改了之后还对不对"变成一条命令——两者都只是语言核的薄包装，但包装里有真正的设计决定。

## 三个核心要素

**1. REPL 的活儿在"判断输入没写完"。**
`fn f() {` 敲了一半，解析必然失败。区别"写错了"和"还没写完"靠解析器的 `Error.Incomplete` 标记：凡是在文件尾（EOF）位置缺东西，就标记为不完整，REPL 换提示符继续等。ling 的多行体验：`fn greet(name) {` 回车进入 `...` 续行，`}` 回车才执行。

**2. 会话状态 = 一个不销毁的解释器。**
每次输入都调 `EvalChunk`：表达式求值后打印 `=> 值`，声明则落进常驻的全局环境。于是 `let x = 10` 之后 `x * 2` 能算出 20。REPL 没有自己的状态管理——状态就是解释器的 `Globals` 环境活着没销毁。

**3. 测试约定用"文件名 + 函数名前缀"顶替框架。**
`ling test` 扫当前目录 `*_test.ling`，执行所有 `test` 前缀的无参函数，`assert` 失败即红。没有测试框架、没有断言库、没有注解——Go 的 `go test` 同款思路：约定优于配置，编译器自带的子命令够了。这是 decisions.md #8 工具链裁剪的直接产物：不留 LSP/调试器/包管理器的位置，只留编译器 + REPL + 格式化器。

## 最容易混的误解

误解：REPL 就是 while 循环套解释器。
活儿在三处：续行判定（上面第 1 条）、错误的存活（一条输入报错，之前的 `let` 绑定必须还在）、以及"表达式打印值、声明静默"的双模式。少任何一条，REPL 就是个一次性的计算器。另一个误解：测试运行器可以后补——ling 的经验是 M2 就要它：`examples/selftest` 的 5 条用例本身就是语言的回归防线，`ling test` 一条命令全量复验。

## 在本项目里看什么

- `cmd/ling/cli.go`：`repl()`（约 40 行：续行缓冲、`:quit`/`:help`、双模式输出）、`runTests()`（收集 → 装载 → 依序执行 → 退出码）。
- `internal/syntax/parse_test.go` 的 `Test不完整输入标记`：五条"写了一半"的源码都必须标 Incomplete——REPL 的续行体验是被测试钉死的行为。
- `examples/selftest/lang_test.ling`：注意它用什么写测试——`assert(1 + 2 * 3 == 7)`。语言从 M2 开始"吃自己的狗粮"，M4 移植 bilibili 提取器时，同一套约定直接复用。
- 一条安全边界：v0.1 CLI 不收路径参数（`ling run` 固定跑当前目录 `main.ling`），文件输入因此不存在 `..` 穿越面。这是安全审查留下的设计约束，写进了 spec §5。

## 行业对照

Python 的 REPL 是树遍历解释器加循环的教科书；Node.js 之于 V8、irb 之于 Ruby 同构。Go 至今没有官方 REPL——编译型语言做 REPL 的成本在"增量编译单元"的划分，而 ling 的树遍历架构天然免费获得。Lisp 社区说"语言即 REPL 体验"，这圈包装决定了语言的第一手感。
