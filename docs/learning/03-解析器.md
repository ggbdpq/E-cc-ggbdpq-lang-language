# 03 - 解析器：把记号流长成语法树

## 一句话定义

解析器（Parser）按语法规则把记号流组装成树（AST，抽象语法树），`1 + 2 * 3` 从"一排词"变成一棵"乘法长在加法右边"的树——树的形状就是计算的顺序。

## 三个核心要素

**1. 递归下降是骨架。**
每种语法结构对应一个函数：`parseStmt` 解析语句、`parseBlock` 解析块、`parseType` 解析类型，函数互相调用天然形成嵌套结构，就像用"句子包含从句包含从句"的方式读文章。ling 的 `internal/syntax/parse.go` 全部由这类函数组成，没有生成器、没有表格。

**2. Pratt 解析器处理优先级。**
表达式解析用的是 Pratt 技术：每个运算符有一个优先级数字（ling 的表在 `precOf`：`||` 是 1，`*` 是 7），`parseExpr(minPrec)` 只吞下优先级不低于 minPrec 的运算符。类比：排电梯——优先级低的运算符"让"先算的先上。`1 + 2 * 3` 里 `*` 优先级 7 大于 `+` 的 6，所以 `2 * 3` 先结合成子树。

**3. 歧义要靠额外规则裁决。**
`if p { ... }`：`p` 后面的花括号是"if 的块"还是"名为 p 的空结构体字面量"？ling 的裁决是 `noStruct` 计数器：在 if/while/match 头部与 for 迭代器位置禁止裸 struct 字面量，加括号即可恢复（`if (Point{x:1}).x > 0`）。这是 Rust 同款规则（Rust 社区为此争论过多年）。

## 最容易混的误解

误解：AST 节点要和语法条目一一对应，语法里写了什么就建什么节点。
实际上 AST 是给求值器服务的，可以合并可以细分。ling 的一个真实例子：`..` 区间在 Pratt 循环里本来会生成 `Binary{Op: Dot2}`（二元运算节点），但求值器需要独立的 `RangeEx` 节点，最终在 `parseExpr` 里为 `..` 单独建节点。测试先行让这个错位在"未知算术运算"的报错里现形——这正是不对着实现写测试的价值。

## 在本项目里看什么

- `internal/syntax/parse.go` 的 `parseExpr`/`parseUnary`/`parsePostfix` 三层结构：二元循环、一元前缀、后缀链（调用/索引/字段/`?`），是 Pratt 的最小完整样本。
- `parseMatch`：为什么 match 分支之间"需要换行"能被检查出来——词法层保住了换行记号（指南 02），解析层才能要求它。
- `Error.Incomplete` 字段：解析器在"输入中途截断"时打标记，REPL 靠它决定"继续等下一行"还是"报错"（指南 05 有续）。
- 对应测试 `internal/syntax/parse_test.go`：不完整输入、保留字、控制头歧义、match 作实参。

## 行业对照

递归下降 + Pratt 是当下手写解析器的主流组合：Rust（rustc）、Lua、Go（部分）、TypeScript 编译器都是这条路。路线上的另一派是解析器生成器（yacc/ANTLR），适合语法频繁变动的场景，代价是报错信息和调试体验差一截。ling 手写，因为报错质量（第几行、期望什么）是 v0 唯一的开发者体验。
