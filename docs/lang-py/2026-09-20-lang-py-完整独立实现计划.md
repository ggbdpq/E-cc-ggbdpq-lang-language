# 2026-09-20-lang-py-完整独立实现计划

> 项目：`lang-py`  
> 定位：使用 Python 独立实现与 lang-go 同一门语言  
> 目标：一次性达到当前 lang-go 完整能力面，并在 v0.9 完成后通过最终契约同步  
> 工作模式：Full-Parity Working Tree，开发阶段不提交 Git


## 0. 最高优先级约束

本项目是 **lang-go 的独立实现（independent implementation）**。`lang-py` / `lang-ts` 只表示编译器自身使用的宿主语言，所实现的源语言、语法、静态语义、动态语义、诊断协议、Agent Contract 和 Conformance Contract 必须与 lang-go 保持一致。

### 0.1 一次性完整复刻，开发期间禁止提交

本轮采用 **Full-Parity Working Tree** 模式：

```text
侦察 lang-go 当前完整能力
        ↓
一次性实现完整 lang-py / lang-ts
        ↓
持续测试、修复、对齐
        ↓
v0.9 最终契约同步
        ↓
全量 Conformance / Differential / Contract 验证
        ↓
输出建议 Commit Plan
```

整个实现阶段：

```text
禁止 git init
禁止 git add
禁止 git commit
禁止 git tag
禁止 git push
禁止 cherry-pick
禁止 rebase
禁止照着 lang-go 的历史提交逐个复刻
```

如果目标目录已经处于 Git 仓库中，也不得修改 Git 历史或创建提交。

所有代码先连续保留在工作区。只有完整复刻通过最终验收后，输出一份“建议如何拆分提交”的 Commit Plan，**本轮不执行任何提交**。

这样做的目的，是让 Python / TypeScript 实现围绕当前完整语言契约设计，而不是被 lang-go 的历史重构路径绑架。

### 0.2 v0.9 并行开发同步规则

lang-go 的 v0.9 正在另一个工作流中实施，因此：

1. 开工时读取 lang-go 当前 HEAD、现有 v0.1～v0.8 计划以及 v0.9 Draft。
2. 对稳定部分直接实现。
3. 遇到 v0.9 尚未最终裁定的语义，不允许自行发明答案，记录为 `SPEC-GAP`。
4. 不因为 `SPEC-GAP` 阻塞其他稳定模块的开发。
5. 最终验收前必须重新读取 lang-go 最新：
   - `specs/`
   - Rule Catalog
   - diagnostics contract
   - Agent Contract / schemas
   - `conformance/`
   - runner contract
   - v0.9 最终 ADR
6. 做一次 **Final Contract Sync**，关闭全部可关闭的差异。
7. 只有最终 lang-go Conformance Contract 能裁决语义，Go 内部源码只能作为实现参考，不能成为最高规范。

### 0.3 禁止“翻译 Go 代码”

允许阅读 Go 实现以理解工程行为和发现遗漏，但禁止：

```text
Go struct 逐个翻译
Go 文件逐个翻译
Go package 机械映射
Go 控制流逐行复制
Go 私有 helper 直接复制
```

应采用宿主语言最自然、最成熟的工程范式重新实现相同语义。

最终比较的是：

```text
Valid / Invalid Decision
Name Binding
Type Result
HIR / IR Semantic Meaning
Diagnostics Identity
Observable Runtime Behavior
Agent Contract
Conformance Result
```

不是源码长得像不像 Go。

## 2. Python 工程原则

采用现代 Python 工程方式，优先标准库和少量高价值开发依赖。

推荐：

```text
pyproject.toml
src/lang_py/
tests/
```

核心原则：

- 全项目类型注解。
- 核心模型避免无约束 `dict[str, Any]`。
- AST / HIR / IR 优先使用 `dataclass(frozen=True)`、`Enum`、`Protocol`、显式联合类型。
- SymbolId / NodeId / DiagnosticCode 使用明确值对象或 NewType 风格，避免裸 int/string 到处传播。
- Semantic Core 尽量写成纯函数和显式上下文对象。
- 不依赖 Python 动态行为替代语言自己的类型规则。
- 不用异常承担普通语言级 `Result` 语义；宿主异常只处理真正的实现故障。
- IO、进程调用、文件系统与 Semantic Core 分层。
- CLI 只做编排，不承载语言语义。
- 保持 deterministic ordering。
- `Any` 只允许出现在真正的动态边界。

开发工具建议采用项目当时可用的稳定版本：

```text
pytest
ruff
mypy 或 pyright（二选一，优先已有环境）
```

不要为了工具链引入大体积运行时框架。

## 13. Phase J：Python 特有风险审查

重点防止：

### Dynamic Typing Leakage

Python 自身是动态语言，但 lang-go 的静态语义不能因此放宽。

### Dict Ordering Dependency

即使现代 Python dict 保序，也不要让语言语义意外依赖实现容器的遍历顺序。需要规范的地方显式排序或遵守 source order。

### Exception Leakage

Python traceback 不应成为用户级语言错误协议。

### Mutable Object Aliasing

AST / HIR / IR 使用可变对象时容易产生隐式 alias。核心语义模型优先 immutable。

### Recursion Limit

深 AST/表达式不要默认依赖 Python 递归深度。必要处采用显式 stack 或给出可控诊断。

### Subprocess / Encoding

Go / Node differential runner 必须显式 UTF-8、明确 exit code、stdout/stderr 捕获规则。

- Go / JS backend 可工作。

- `SPEC-GAP` 已关闭或被 canonical spec 明确登记。
