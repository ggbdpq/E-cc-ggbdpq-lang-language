# ADR-0005：赋值目标位置顶层 `?` 传播的合法性

日期：2026-09-25 · 状态：已接受 · 关联：SPEC-GAP-RS-011

## 背景

`x = f()?` 形态（赋值右值为顶层 `?` 表达式）在三套既有实现中行为分裂：
TS/Go 的 checker 误发 E3005（`?` 位置非法），而 Go 解释器运行时正确支持传播；
specs/option-result.md 的 `?` 位置约束针对的是「非 Result 函数体」语境，并未排除
赋值右值位置。lang-rs（第四实现）按 spec 实现并锁定了测试（见其 lang-semantic 契约）。

## 决定

赋值右值位置的顶层 `?` 表达式**合法**：语义 = 常规 `?` 传播——求值右值，
`Err` 载荷从当前函数立即传播（若所在函数未注解 Result，仍按 E3005/E3006 拒绝）。
checker 不得因「位于赋值语句」而额外拒绝。

## 依据

1. specs/option-result.md 的 `?` 位置约束语境 = 函数注解，非语句类别。
2. Go 解释器（参考实现运行时面）已支持该形态——运行时语义是 v1.0 冻结面。
3. conformance 语料无此形态 case；不新增 case（避免为已冻结行为扩语料），以各实现单测锁定。

## 影响

- lang-rs：已按本决定实现（无需改动）。
- Go/TS 上游 checker 的误报属实现 bug，是否修复由各自维护节奏决定，不阻塞第五实现。
- 第五实现（lang-cs）checker 直接按本决定实现。
- SPEC-GAP-RS-011 关闭为 RESOLVED_BY_SPEC。

## 扩展（2026-09-27）

表达式语句位置的顶层 `?`（`f()?` 单独成句）亦**合法**：求值 `f()`，`Err` 载荷从当前函数
传播（所在函数未注解 Result 时仍按 E3005 拒绝）。语义与本裁决放行的 `let`/`return`/赋值
三处完全一致——此前五套实现 checker 对该位置误发 E3005，属语句分派漏项而非语义分歧，
五套 checker 已同步按 `inferTry` 路径放行。E3005 的 message 相应微调为
「? 只能出现在 let/return/赋值/表达式语句的顶层」（specs/diagnostics.md 允许 message 微调）。
conformance 语料继续不为此扩语料，以各实现单测锁定。
